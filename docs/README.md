# PIM documents

The documents are a lineage. Each one answers a question the one before it raises, and each names the one it was derived from, so a reader can follow a requirement to the idea that serves it, to the module that carries it, to the decision that fixed it and the work that built it. Read them in order the first time.

**How a change moves through the lineage.** A new obligation is a row in the requirements with an id, an outcome it serves and a harness that will prove it. If it needs a new idea or breaks an entailment of the concept, the intent changes, and that is a decision for Areg. The architecture then shows where the obligation lands and which contract carries it. A consequential choice on the way becomes an ADR, written as Proposed with the alternative it rejects. The plan schedules it behind a gate, and the gate record says what ran. The rules for doing this work, for people and agents, are in the repository's `AGENTS.md`.

**Conventions.** Plain technical English, short sentences, one idea each. Requirement ids (CAP-, PRS-, MET-, GRA-, SEC-, UI-) and decision ids (D1 to D13, ADR-nnn) are stable and cited in code, tests and gate records. Diagrams are Mermaid, C4 where they show structure, so GitHub renders them and a diff shows what changed. Biome formats these files; run `npm run lint`.
